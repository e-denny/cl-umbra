# Prior art, and what is taken from each

Nothing here is copied code. This is the list of ideas, structures and behaviours that the
plan deliberately borrows, plus the failures worth not repeating.

---

## wayflan — the closest thing to phase 0-1

Samuel Hunter's from-scratch Wayland **client** for Common Lisp (BSD-3-Clause). The single
most important precedent for this project: it demonstrates that replacing libwayland in Lisp
produces a better API, not just a purer one.

**Taken:**
- The wire layer's shape: circular in/out buffers, `sendmsg`/`recvmsg` for fd passing, the
  28-fd flush ceiling derived from libwayland's 128-byte cmsg buffer, `MSG_CTRUNC` as fatal.
- The scanner: XML → CLOS metadata → generated `define-interface`/`define-request`/
  `define-event`/`define-enum` forms; enums as keywords; docstrings from protocol text.
- The ASDF extensible-component trick (`:wayflan-client-impl` → our `:wayland-protocol`),
  which makes adding a protocol a one-line build change.
- The stance that undocumented behaviour should mimic libwayland ("good-faith" compatibility),
  rather than being re-invented.
- `wl-proxy-hooks`, the pragmatic hook mechanism for client-side dispatch.

**Not taken:** it is client-only. There is no global/resource model, no per-client object
table, no server-side destroy semantics, no socket accept path. Phase 1 is entirely new
work. We also generate *both* directions from one schema rather than one direction from a
client-specific scanner.

**Attribution:** if any code is adapted rather than reimplemented, the BSD-3-Clause notice is
kept in that file (D13).

## Ulubis — the proof that this can work

Malcolm Still's Common Lisp Wayland compositor (2016-2018, BSD-3). A real compositor with
DRM/GBM and SDL backends, modes, virtual desktops, alt-tab, screenshots, and live hacking
through SLIME.

**Taken:** the ambition, and three concrete lessons:
1. Two backends (one for real hardware, one for development inside X/Wayland) is what makes
   a CL compositor testable. Our headless and nested backends are the same idea, ordered
   earlier.
2. Live modification of a running compositor is the killer feature; it needs a safe
   interruption design, not just a SWANK port (see `architecture.md` §6).
3. Modes/desktops as first-class objects are a good shape for `cl-umbra`'s layouts.

**Not taken:** it depends on `cl-wayland` — CFFI bindings over libwayland — plus 8 other
CFFI shims (`cl-drm`, `cl-gbm`, `cl-egl`, `cl-libinput`, `cl-xkb`) and CEPL. That stack is
exactly what D1/D2 reject: the protocol lives in C, and the Lisp side is callbacks into
opaque structs. Its roadmap (multi-monitor, Xwayland, screen lock, browsers) is still open,
which is the honest measure of how much the binding approach saves you.

## wlroots and tinywl — the decomposition, not the code

wlroots' README calls itself "about 50,000 lines of code you were going to write anyway".
That is the correct framing: the value is the *decomposition* plus the accumulated
knowledge of which abstractions survive contact with real clients.

**Taken:**
- The module boundaries in `docs/framework.md` §1: backend / renderer / allocator /
  scene / output / seat / per-protocol types / session.
- The backend split (DRM, libinput, headless, nested, multi) and autocreation as a
  convenience, not a policy.
- `tinywl` as a conformance target: same features, same behaviours, ~900 lines of policy.
- The frame-clock discipline: render on vblank/page-flip completion, send frame callbacks
  after presentation.
- The output-layout abstraction and the idea that one output global exists per physical
  output, with the compositor owning arrangement.
- The `wlr_scene` idea of a retained tree with per-output layers and damage propagation —
  the abstraction that makes the difference between a demo and a desktop.

**Not taken:** any code, any ABI, `wl_list`, `wl_signal`/`wl_listener`, opaque structs,
vtables, type-tagged nodes, `wlr_xwayland`'s in-process XWM (D12).

## river — layouts as a protocol

A wlroots compositor in Zig with `river-layout-v3`: window layouts are generated by
*separate processes* speaking a small protocol over a socket, so users write layouts in any
language.

**Taken:** the requirement that layout policy must not be hard-wired into the compositor.
Our expression of it differs: layouts are objects/closures in the image (so they can be
redefined live, which is the Lisp advantage), with the eval channel able to host external
generators if we ever want them (open question 2 in `PLAN.md` §10).

**Not taken:** the `wlr` protocol surface it inherits, or the process-per-layout model as the
only option.

## niri — the scrolling layout, and per-output workspaces

**Taken:** the semantics of the scrolling column layout (`cl-umbra` v1's second layout):
columns of fixed width, new windows open as new columns, focus moves between columns, widths
adjust by consuming/expelling neighbours, workspaces are per-output and vertical. Umbriel's
scrolling layout is itself inspired by niri, so this is the shortest path to "functionally
similar".

**Not taken:** animations and the visual language (phase 7), and its Rust architecture.

## Umbriel — the feature target

wlroots + C++23 + a SceneFX fork (`umbrielfx`). MIT. Its README, `docs/user/*` and
`SCOPE.md` are the specification for `cl-umbra`.

**Taken:** the feature taxonomy and the user-facing expectations: scrolling/dwindle/master/
stacking layouts, per-output workspaces, window and layer rules, blur/shadows/animations,
HDR/VRR/tearing/direct scanout/explicit sync, touchpad gestures, input methods, Xwayland,
layer shell, session lock, screencopy, live-reloaded config with diagnostics, and runtime
inspection. Also its discipline: `SCOPE.md` says what the project declines, which is how a
compositor stays maintainable. `cl-umbra` gets the same document with different contents
(v1 = daily driver, no eye candy, per D10).

**Not taken:** SceneFX's rendering model (we start with a plain scene graph and pixman), TOML
as the config language (rejected in D11: it would be a second grammar under the first), and
its IPC layer entirely: with D14 the control surface is the running image, and the eval
channel covers scripts.

## sway, weston, and the clients — conformance oracles

Not sources of design, but sources of truth about what clients actually expect. Weston's
toy clients (`weston-simple-shm`) and `wayland-info` are the smallest possible conformance
suite; sway's bug tracker is a catalogue of xdg-shell edge cases we will otherwise
rediscover.

## The Common Lisp ecosystem

| Library | Use |
|---|---|
| `cffi` / `cffi-grovel` | the FFI boundary; grovel for ioctl numbers, `struct` layouts, constants |
| `closer-mop` | metaclasses for generated protocol classes |
| `plump` | XML parsing of protocol files (build time only) |
| `alexandria` | utilities, `eswitch`, `once-only` |
| `static-vectors` | pinned octet vectors where mmap is not the answer |
| `sb-posix` | `mmap`/`munmap`/`mprotect` — but **no** `memfd_create`, no epoll, no `sendmsg`; those are CFFI |

Known gaps that shape the design: SBCL gives no portable `sendmsg`/`recvmsg` with ancillary
data, no `epoll`, no `timerfd`, no `eventfd`, no `signalfd`, no DRM, no EGL. All of that is
CFFI, and that is expected — they are kernel/driver APIs, not Wayland (D4).

## Things the prior art warns about

- **Buffer lifetime bugs** are the most common source of frozen clients (wlroots' issue
  history). Hence the explicit "released exactly once, after presentation" contract.
- **Serial validation** is skipped by small compositors and is a security hole. Hence
  `valid-serial-p` as a first-class framework concept.
- **Advertised-but-unimplemented globals** break real applications in confusing ways. Hence
  the "declare a global only when complete" rule.
- **Blocking in the main loop** (a debugger, a synchronous read, a slow composite) freezes
  every client at once and looks like a compositor crash. Hence D9 and the watchdog.
- **Animations and effects retrofitted** onto an immediate-mode renderer are a rewrite.
  Hence the retained scene graph from phase 2, even though v1 does not animate.
